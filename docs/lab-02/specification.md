# Lab 2 Sprint Engineering Specification

Status: **DRAFT — pending student review and approval.** Do not hand to the AI coding agent until this file, `api-spec.md`, `ui-spec.md`, and `tests.md` have been reviewed, corrected, and approved.

## 1. Sprint Goal

Deliver a Requester-facing IT ticketing MVP so that a selected Development Requester can create a support ticket, find it in My Tickets, inspect it in Ticket Detail, and manage its attachments — establishing the Zen Green UI foundation that later sprints will reuse.

## 2. Stakeholder Request Interpretation

The IT department wants end users (Requesters) to submit support tickets themselves instead of going through IT staff. A Requester must be able to describe a problem, classify it, attach evidence, and track it afterward, without seeing or affecting other Requesters' tickets. Because real login does not exist yet, the sprint needs a temporary "pick who you are" screen so the rest of the flow can be tested as if per-user ownership already worked, ready to be replaced by real authentication in Lab 3.

## 3. Scope

### Included

- Development Requester Selection screen (testing-only identity switch).
- Create Ticket: form, validation, submission, Ticket Number generation, initial attachment upload.
- My Tickets: paginated, searchable, filterable, sortable list scoped to the selected Requester.
- Requester Ticket Detail: read-only ticket fields plus attachment list.
- Attachment lifecycle: add to an existing ticket, download or preview an active attachment, soft-remove with a reason.
- Ownership enforcement on every Requester-scoped read/write.
- Zen Green Theme and reusable form/list/badge/validation/loading/empty/error/responsive conventions.
- Reference data: Categories (existing from Lab 1), Related Systems (new), Development Requesters (new).

### Excluded

- Real authentication: login, logout, passwords, sessions, tokens, role-based authorization.
- IT Staff dashboard, queue, ticket claiming/reassignment, IT Priority.
- Public Comments, Internal Notes, Actions Taken.
- Any status transition beyond the initial `NEW` status (resolve, close, reopen, cancel).
- Administrator management of users, Requesters, roles, or reference data (no Category/Related System/Requester CRUD UI).

## 5. Business Rules

| ID | Rule |
|----|------|
| BR-01 | The official Ticket Number is generated by the backend and must be unique. *(fixed by handout)* |
| BR-02 | A new Ticket begins with Current Status `NEW`. *(fixed by handout)* |
| BR-03 | Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication. *(fixed by handout)* |
| BR-04 | Only active Development Requesters appear in the selector; inactive Requesters are never listed or selectable. |
| BR-05 | A Ticket's owner is fixed to the Requester selected at creation time; ownership does not change during Lab 2. |
| BR-06 | A Requester may only view, list, or act on Tickets and Attachments they own. Requests for another Requester's Ticket or Attachment return `404 Not Found` (not `403`), so existence is never confirmed to a non-owner. |
| BR-07 | Ticket Date is the server timestamp recorded at creation; it is read-only and never entered by the Requester. |
| BR-08 | Category and Related System selected on a Ticket must reference existing reference-data rows at creation time. |
| BR-09 | Ticket Summary is required, is trimmed of leading/trailing whitespace, and must be 5–150 characters after trimming. |
| BR-10 | Description is required, is trimmed, and must be 10–5000 characters after trimming. |
| BR-11 | Requested Priority is required and must be one of `LOW`, `MEDIUM`, `HIGH`, `URGENT`. The Create Ticket form starts with no priority selected; the Requester must explicitly choose one, and submitting without a choice is a validation error like any other required field. |
| BR-12 | Allowed Attachment types are JPG, JPEG, PNG, WEBP, and PDF only. *(fixed by handout)* Validated by checking **both** the file extension and the client-declared `Content-Type` (via multer's `file.mimetype`) against the allow-list — not content-sniffing the file's actual bytes. Whatever value is accepted is the only value ever stored and later served back as `Content-Type`, so a mislabeled file can produce a broken preview but never an unexpected `Content-Type` being served (BR-33's inline preview stays confined to the four allowed image/PDF types). |
| BR-13 | Maximum Attachment size is 5 MB per file. *(fixed by handout)* |
| BR-14 | A Ticket may have at most 5 active (non-removed) Attachments at any time; removed Attachments do not count toward the limit. *(fixed by handout)* |
| BR-15 | Attachment removal is a soft removal: the row and its metadata remain in the database, but a removed Attachment can no longer be downloaded or previewed. *(fixed by handout)* |
| BR-16 | Removing an Attachment requires a removal reason, trimmed, 3–300 characters. |
| BR-17 | Ticket creation and attachment upload are independent steps. If a Ticket is created successfully but an attached file fails to upload, the Ticket is still created; the client reports which files failed and lets the Requester retry adding them from Ticket Detail. No partial Ticket rollback occurs because of an attachment failure. |
| BR-18 | The Create Ticket Submit control is disabled and shows a busy state for the duration of the request, preventing duplicate submissions from repeated clicks. Lab 2 does not implement a server-side idempotency key; this client-side guard is the documented duplicate-submission control for this sprint. |
| BR-19 | When Create Ticket validation fails (client or server), all previously entered field values are preserved and field-level error messages are shown; no field is silently cleared. |
| BR-20 | When Ticket creation fails due to a network or server error, the form values are preserved, a safe retryable error message is shown, and no Ticket Number is displayed unless a Ticket was actually saved. |
| BR-21 | My Tickets search matches Ticket Number or Ticket Summary using a case-insensitive substring match. |
| BR-22 | My Tickets default sort is Ticket Date descending, with Ticket Number descending as a secondary sort for stable ordering among same-timestamp tickets. |
| BR-23 | My Tickets pagination defaults to page size 10 (allowed sizes: 10, 20, 50). Invalid or out-of-range `page`/`pageSize` query values fall back to the default rather than producing an error. |
| BR-24 | My Tickets distinguishes an **empty state** (the Requester owns zero Tickets) from a **no-results state** (the Requester owns Tickets, but the current search/filter combination matches none). |
| BR-25 | If no active Development Requesters exist, the Requester Selection screen shows an empty state and disables Continue; the Requester cannot enter the rest of the application. |
| BR-26 | Switching the Development Requester clears any Requester-scoped data already loaded in the client (Tickets, Ticket Detail) and reloads it for the newly selected Requester. |
| BR-27 | The selected Development Requester identity is stored client-side (browser session storage) and sent to the backend as an `X-Dev-Requester-Id` header on every Requester-scoped request. This header is a testing convenience, not a security credential — the backend trusts it only because Lab 2 explicitly excludes real authentication. It will be replaced by a server-derived identity from an authenticated session in Lab 3. |
| BR-28 | If `X-Dev-Requester-Id` is missing, does not match an existing Development Requester, or matches an inactive Development Requester, every Requester-scoped endpoint returns `401 Unauthorized` and the client returns the user to the Requester Selection screen. |
| BR-29 | The Ticket Number is generated per calendar month (`TCK-YYYYMM-####`, sequence resets at the start of each month) using a database-level atomic counter increment, so concurrent Ticket creation in the same month cannot produce a duplicate number. |
| BR-30 | My Tickets filters (`categoryId`, `relatedSystemId`, `requestedPriority`, `status`) combine with AND semantics — a Ticket must match every supplied filter to appear in results. A filter value that matches zero Tickets, including a `categoryId`/`relatedSystemId` that does not exist, returns an empty result set, not an error. |
| BR-31 | If a Development Requester who owns Tickets is deactivated, their Tickets remain in the database untouched, but the Requester can no longer select themselves in the selector (BR-04) or access any of their own Tickets or Attachments (BR-28 forces `401` on every Requester-scoped call). Lab 2 has no reactivation mechanism (Admin scope excluded), so this is an accepted consequence of the testing-only selector, not a data-loss bug. |
| BR-32 | An Attachment's database row is created only after its file has been successfully written to disk (write-then-record order). If the disk write fails for any reason, the API returns `500` and no Attachment row is created — the parent Ticket is unaffected either way, and no metadata is ever left pointing at a missing file. |
| BR-33 | Active image Attachments (JPG, JPEG, PNG, WEBP) can be previewed inline in the browser via a dedicated preview endpoint that serves the file with `Content-Disposition: inline`. PDF Attachments are download-only — no inline preview is offered for PDFs. Preview is available only for active (non-removed) Attachments; the same ownership (`404`) and removed (`410`) rules apply as the download endpoint. |
| BR-34 | If Download or Preview is requested for an Attachment whose database row is active but the underlying file is missing from disk (a data-integrity edge case not expected under normal operation, given BR-32's write-then-record ordering — e.g. the file was deleted outside the application), the API returns `500` with a safe "file unavailable" message rather than crashing or serving a broken response; the client shows the same safe message instead of attempting a broken download/preview. The check happens reactively at request time, not via a background scan. |
| BR-35 | An Attachment can be soft-removed only once. Attempting to soft-remove an Attachment that is already removed returns `409 Conflict`; it does not silently succeed and does not overwrite the original `removedAt`/`removedReason`. |
| BR-36 | My Tickets query parameters are forgiving by design: any `requestedPriority`, `status`, `sortBy`, or `sortDir` value that isn't one of the allowed enum values, and any `categoryId`/`relatedSystemId` that is missing, non-numeric, or malformed, is treated as if that parameter were not supplied at all — no filter or sort override is applied for it, and `GET /api/tickets` never returns `400` for a malformed query. This generalizes BR-23's pagination fallback and BR-30's filter-value fallback into one consistent rule across every query parameter on the endpoint. |

### 5.1 Create Ticket Field Reference

Consolidated answer to the handout's §4.4 request ("which fields are required, which are editable, the validation limits, trimming rules, allowed values") — one row per field captured or shown on Create Ticket:

| Field | Source | Required | Editable after creation | Validation | Rule(s) |
|---|---|---|---|---|---|
| Ticket Number | System-generated | N/A | No | Unique, `TCK-YYYYMM-####` | BR-01, BR-29 |
| Ticket Date | System-generated (`createdAt`) | N/A | No | Server timestamp at creation, never Requester-entered | BR-07 |
| Requester | System-derived from selected identity | N/A (not chosen per-Ticket) | No | Must be an active `RequesterUser`, taken from `X-Dev-Requester-Id` | BR-05, BR-27, BR-28 |
| Category | Requester-selected | Yes | No | Must reference an existing `Category` row | BR-08 |
| Related System | Requester-selected | Yes | No | Must reference an existing `RelatedSystem` row | BR-08 |
| Ticket Summary | Requester-entered | Yes | No | Trimmed; 5–150 characters | BR-09 |
| Requested Priority | Requester-selected | Yes, no pre-selected default | No | One of `LOW`/`MEDIUM`/`HIGH`/`URGENT` | BR-11 |
| Description | Requester-entered | Yes | No | Trimmed; 10–5000 characters | BR-10 |
| Attachments | Requester-uploaded | No (optional at creation) | Yes — more can be added later from Ticket Detail (FR-12) | ≤5 MB each; JPG/JPEG/PNG/WEBP/PDF only; ≤5 active per Ticket | BR-12, BR-13, BR-14 |

All required-field and length validation is enforced identically on the client (immediate feedback) and the server (source of truth) — the client check is a UX convenience, never the only check.

## 7. Data Changes

New Prisma models (in addition to the existing `Category`):

- **`RequesterUser`** — `id`, `name`, `email` (unique), `active` (Boolean, default `true`), `createdAt`. Represents the Lab 2 Development Requester, explicitly not a real auth-backed user account. Seed: at least 4 active rows + at least 1 inactive row (§5.3 of the handout), inserted idempotently (upsert on `email`, safe to re-run without duplicating).
- **`RelatedSystem`** — `id`, `name` (unique), `createdAt`. Mirrors `Category`'s shape; no `active` flag because Lab 2 excludes Admin/reference-data management, so every seeded row is implicitly usable. Seed: at least 6 rows (e.g. Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Printer, Corporate Laptop), inserted idempotently (upsert on `name`, matching the existing `Category` seed pattern from Lab 1).
- **`Ticket`** — `id`, `ticketNumber` (String, unique, backend-generated per BR-29), `requesterId` (FK → RequesterUser), `categoryId` (FK → Category), `relatedSystemId` (FK → RelatedSystem), `summary`, `description`, `requestedPriority` (enum `LOW`/`MEDIUM`/`HIGH`/`URGENT`), `currentStatus` (enum, `@default(NEW)`, only `NEW` used this sprint per BR-02), `createdAt`, `updatedAt`.
- **`Attachment`** — `id`, `ticketId` (FK → Ticket, `onDelete: Cascade` — Lab 2 has no Ticket-deletion feature, but a Ticket should never leave orphaned Attachment rows if one is ever removed at the DB level), `originalFilename`, `storedFilename` (**unique**, generated as a UUID v4 + the original file extension — e.g. `3fae2b1c-....jpg` — decoupled from user input so it can never collide or be guessed from the original filename), `mimeType`, `sizeBytes`, `uploadedAt`, `removed` (Boolean, default `false`), `removedAt` (nullable), `removedReason` (nullable).
- **`TicketNumberCounter`** — `yearMonth` (String, e.g. `"202608"`, unique/primary key), `lastSequence` (Int, default `0`). Backs the atomic monthly counter in BR-29. Two concurrency cases, both inside the same transaction as the `Ticket` insert:
  - **Row already exists for this month**: atomic `UPDATE ... SET "lastSequence" = "lastSequence" + 1 RETURNING "lastSequence"` (Prisma's `{ increment: 1 }` update) — race-free by construction.
  - **First Ticket of a new month** (row doesn't exist yet): a plain `upsert` is *not* enough on its own — if two requests both see no row and both attempt to create one, only one `INSERT` wins on the unique `yearMonth` constraint, and the other throws a unique-violation. The counter logic must catch that specific error and retry as the update path above, rather than surfacing a `500` to the Requester. This retry-on-conflict handling is exactly what AC-30 exercises.

**Note on `Category`**: unchanged from Lab 1 (`id`, `name`, `createdAt`). No `active` flag is added because Category management is Admin scope (excluded from Lab 2) and there is no mechanism to deactivate one; `GET /api/categories` returning all rows already satisfies "retrieve active Categories."

### 7.1 Relationships

- One `RequesterUser` owns many `Ticket`s; one `Ticket` belongs to one `RequesterUser`.
- One `Ticket` has many `Attachment`s; one `Attachment` belongs to one `Ticket`.
- One `Category` is used by many `Ticket`s; one `RelatedSystem` is used by many `Ticket`s.

### 7.2 Indexes, constraints, and justified design decisions

- `ticketNumber` is unique (enforced at the database level, not just application logic).
- `requesterId`, `categoryId`, `relatedSystemId` on `Ticket`, and `ticketId` on `Attachment`, are indexed foreign keys (Prisma creates these automatically) to keep My Tickets filtering and Ticket Detail lookups fast.
- `createdAt` on `Ticket` is indexed to support the default sort without a full table scan once ticket volume grows.
- **Justified decision**: `currentStatus` is modeled as a Prisma `enum` rather than a `Status` reference table, even though later labs will add more statuses and a workflow. An enum is simpler to migrate for the single-value `NEW` case Lab 2 needs, and Prisma enum migrations are additive (new values can be appended) — a reference table would add join overhead and CRUD scope for zero present benefit, since Lab 2 explicitly excludes status transitions and Admin management of reference data. Lab 3 can migrate `currentStatus` to a reference table if the workflow needs metadata (color, order, terminal-state flag) that an enum can't hold.
- Soft removal on `Attachment` is represented by a `removed` boolean plus `removedAt`/`removedReason`, rather than deleting rows or moving them to an archive table, so metadata stays queryable from the same table Ticket Detail already reads.
- **Search is not index-backed**: `BR-21`'s case-insensitive substring match (`ILIKE '%term%'`) on `ticketNumber`/`summary` cannot use a standard B-tree index because of the leading wildcard. This is an accepted limitation at Lab 2's data scale (a handful of seeded Requesters and their Tickets); a production-scale version would need a trigram (`pg_trgm`) or full-text index, deferred to a later lab if ticket volume ever warrants it.
- **Schema evolution note for Lab 3**: `RequesterUser` is deliberately kept separate from any future authenticated `User`/account model rather than pre-emptively adding auth fields (password hash, etc.) now, since Lab 2 explicitly excludes authentication. The expected Lab 3 migration path is either (a) add auth fields directly onto `RequesterUser` and repurpose it as the real user table, or (b) introduce a `User` table and add a nullable `userId` FK onto `RequesterUser` to link a dev-testing identity to a real account. `Ticket.requesterId` continues to point at `RequesterUser.id` either way, so no Ticket/Attachment data needs to move.

## 8. API Contract

Full detail in `api-spec.md`. Endpoints:

| Capability | Method & Path |
|---|---|
| Active Development Requesters | `GET /api/requesters` |
| Categories | `GET /api/categories` |
| Related Systems | `GET /api/related-systems` |
| Create Ticket | `POST /api/tickets` |
| List own Tickets (search/filter/sort/paginate) | `GET /api/tickets` |
| Get one owned Ticket | `GET /api/tickets/:id` |
| Upload Attachment | `POST /api/tickets/:id/attachments` |
| Get Attachment metadata | `GET /api/attachments/:id` |
| Download active Attachment | `GET /api/attachments/:id/download` |
| Preview active image Attachment | `GET /api/attachments/:id/preview` |
| Soft-remove Attachment | `DELETE /api/attachments/:id` |

All Requester-scoped endpoints — every endpoint above except `GET /api/requesters`, `GET /api/categories`, and `GET /api/related-systems` (all three are unauthenticated reference-data/identity-establishing reads; requiring a header to discover who you can be would be circular) — require the `X-Dev-Requester-Id` header (BR-27, BR-28).

## 11. Assumptions and Decisions

- **Local file storage**: Attachments are stored on local disk under `server/uploads/` (gitignored), with a generated safe filename decoupled from the user-supplied original filename. Files are served only through the ownership-and-removal-checked `GET /api/attachments/:id/download` endpoint — never via Express static file serving — so a removed or not-owned file can never be fetched by guessing a static path. This is documented as a Lab 2-only choice; a production system would use object storage.
- **New dependencies**: `react-router-dom` is added to the client to route between the four screens; `multer` is added to the server to parse multipart Attachment uploads. Both are within Lab 2 scope and necessary for the required screens/endpoints.
- **`react-router-dom` audit advisory (reviewed, accepted)**: `npm audit` flags every current 7.x release with at least one open advisory; the newest release (`7.18.2`, pinned) has the fewest and they are all specific to react-router's server-rendering "framework mode" — RSC (React Server Components) redirect/action handling, SSR hydration, and server-action CSRF. Lab 2's client is a plain Vite SPA using client-side `<BrowserRouter>`/`<Routes>` only, with no SSR, no data loaders/actions, and no RSC — so none of the vulnerable code paths are reachable. Using the latest version minimizes exposure versus pinning to an older release to dodge one advisory while re-exposing several others that were since patched. Revisit if `react-router` ships a clean release, or before this app ever adopts SSR/RSC/data-router server actions.
- **Dev-identity transport**: the handout (§4.4, §6.1) explicitly leaves the storage/transport mechanism for the selected Requester to the student. The selected Development Requester's ID is sent as an `X-Dev-Requester-Id` request header (BR-27/BR-28) — kept separate from the `GET /api/tickets` search/filter/sort/pagination query string — rather than a query parameter, so every Requester-scoped endpoint has one consistent, easy-to-remove-in-Lab-3 place to read identity from, and so identity never appears in a URL, browser history, or server access log.
- **API response shape**: endpoints without pagination (`/api/requesters`, `/api/categories`, `/api/related-systems`) return a bare array, matching the existing Lab 1 `/api/categories` convention. Only the paginated `GET /api/tickets` endpoint returns the `{ data, meta }` wrapper, since it is the only endpoint that needs pagination metadata — this avoids a gratuitous breaking change to the Lab 1 endpoint.
- **Requested Priority values**: `LOW | MEDIUM | HIGH | URGENT`, with no pre-selected default on the Create Ticket form (BR-11) — the Requester must make a deliberate choice, consistent with treating it as a genuinely required field.
- **Field length limits**: Summary 5–150 chars, Description 10–5000 chars, removal reason 3–300 chars (BR-09, BR-10, BR-16) — chosen to be generous enough for real support requests while still catching empty/placeholder input; enforced identically on client and server.
- **Ticket Number format**: date-based, `TCK-YYYYMM-####` (BR-29), so the number itself communicates roughly when a Ticket was raised — more meaningful to a Requester or IT Staff scanning a list than an opaque running total, at the cost of needing a small `TicketNumberCounter` table and an atomic increment to avoid collisions under concurrent creation (see §7, §7.2).
- **Ownership failures return 404, not 403**: chosen so a Requester probing another Requester's Ticket ID cannot even learn that the ID exists (BR-06).
- **Attachment preview scope**: only image types (JPG/JPEG/PNG/WEBP) get inline preview (BR-33); PDF stays download-only rather than embedding a PDF viewer, keeping the preview feature to a small, well-tested surface for this sprint.
- **Filter semantics**: My Tickets filters combine with AND, and a filter referencing a non-existent reference-data ID simply yields zero results rather than a `400` (BR-30) — consistent with how most list-filtering APIs treat unmatched filter values, and simpler for the client than special-casing "filter value doesn't exist" as an error.
- **My Tickets columns vs. the handout's example**: the handout's example column list includes "Last Updated," but Lab 2 Tickets are immutable after creation (no comments, status changes, or edits are in scope), so `createdAt` ("Ticket Date") is the only meaningful timestamp this sprint and is shown instead of a separate "Last Updated" column. The `updatedAt` field still exists on `Ticket` for forward-compatibility, but is not surfaced in the UI until a later lab actually changes Tickets after creation.
- **No Ticket "edit mode" in Lab 2**: the only screen modes are Create (Create Ticket) and View (My Tickets, Ticket Detail). Ticket fields (Category, Summary, Priority, etc.) are never editable after creation — only Attachment actions (add/download/preview/remove) are mutable from Ticket Detail, and those are treated as their own inline actions rather than a form "edit mode."
- **"IT Priority" badge (handout §8.8) does not apply to Lab 2**: the handout's UI style-checking example mentions badge consistency for "Requested Priority, IT Priority, and Current Status," but IT Priority is an IT-Staff-owned field explicitly excluded from Lab 2 scope (§3). Only Requested Priority and Current Status badges exist this sprint; IT Priority is intentionally omitted, not overlooked.
- **Attachment upload uses `XMLHttpRequest`, not `fetch`, on the client**: to show a real percentage progress bar during upload (AC-39, `ui-spec.md` §6), the client needs `upload.onprogress`, which the Fetch API does not expose. This is a deliberate, scoped exception to the fetch-based pattern used elsewhere in the client (`App.tsx`, all other Lab 2 API calls) — isolated to the single attachment-upload call site, not a wholesale switch.
- **Missing-file detection is reactive, not a background job (BR-34)**: checked only at the moment a Download/Preview request is made (`fs.existsSync` before streaming), rather than a scheduled integrity scan. A background scanner would need somewhere to report findings, but Admin functionality is out of Lab 2 scope, so there is no surface to act on such a report yet — reactive checking is the right-sized fix for this sprint.
- **Test files beyond the handout's minimum structure (§12)**: `tests.md` adds a few files not listed in the handout's minimum table — `server/tests/lab-02/requesters.api.test.ts`, `client/.../lab-02 tests/RequesterSelection.test.tsx`, and `e2e/lab-02/responsive.spec.ts` — to keep Requester-selector and responsive-screenshot tests in their own files rather than folded into the four named files. These are additions on top of the required minimum, not substitutes for it; every explicitly named file in §12 still exists with its required coverage.
